# 结构总图：这套体系由什么组成、谁拥有什么、什么必须永远成立

> 阅读顺序：**本文（结构）** → `README.md`（人看的入口：来源分类、目标一览、硬规则）→ `syncing-skills/`（agent 看的**操作**）→ `docs/adr/`（难回退决定的理由）→ LLMWiki 合成页（为什么这样定 + 事故教训）。
> 一句话：**内容以源头为准，应该有什么以声明为准，搬东西靠脚本，对不对由只读判定说话。**

## 一、五层，每层只有一个权威

| 层 | 回答 | 权威在哪 | 谁能写 |
|---|---|---|---|
| **L0 权威** | 这个技能**内容**以谁为准？ | 自建 = GitHub 仓库 clone；第二个来源 = LLMWiki 仓库；第三方 = **该平台**的 npx 仓库层；手工 = **无权威**（只有账） | 人（前两者）、`npx skills`（第三方）、人（手工） |
| **L1 声明** | 什么**应该**出现在哪里？ | 四处（见第二节） | 人写 + 自检把关 |
| **L2 实体** | 字节**实际**在哪？ | 各平台的仓库层与面目录 | 只由 L3 的机制写 |
| **L3 机制** | 谁**搬东西**、谁清理？ | `npx skills` · `ensure_junctions.ps1` · `sync-wsl.sh` · `gen-skills-table.py` | 脚本 |
| **L4 判定** | 现在**对不对**？ | `check_distribution.py` | **没有任何人**——它只读、永不写 |

分界最重要的一条：**L3 动手，L4 只说话**。任何"修复"都必须走 L3；L4 一旦写文件，判定与事实就会互相污染。

## 二、声明层是四处，各管一段

这是最容易被误解的地方：**没有单一一处声明**，四个声明处有四种权威形态。

| 声明处 | 声明什么 | 谁在维护 | 消费者 |
|---|---|---|---|
| `scripts/distribution-targets.json` | 有哪些面、每面期望哪些来源、什么角色、是否本机必需 | 人写 JSON；`check_distribution.py` 自检把关（字段 / 取值 / id 重复 / 登记表 token） | 两个同步脚本、判定、生成器、LLMWiki 的 `check_skill_links.py` |
| `manual-skills.md` | 哪些**尚未纳入 npx** 的名字在哪几个面 | 人写表，逐行 | 判定（`manual` 池） |
| 各平台的 `.skill-lock.json` | 第三方**有哪些**、什么版本 | `npx skills` 自己写 | 判定（`thirdparty` 池）、同步脚本（建链名单） |
| 仓库根（含 `SKILL.md` 的目录） | 自建**有哪些** | 文件系统即声明（"仓库即列表"） | 判定（`selfbuilt` 池）、同步脚本 |

期望集合是这四处的并集：`expected(面) = 该面 expect 声明的池 ∩ 各池的当前内容`。
所以"某平台少了一个技能"可能来自**四处中的任何一处**变了——排查先问"是哪一层的声明变了"，而不是先看目录。

## 三、实体层的三种形态（`role` 的三种取值）

| `role` | 平台 | 物理形态 | 谁建 | 例 |
|---|---|---|---|---|
| `junction` | Windows | 目录联接 | `ensure_junctions.ps1`（CLI 也会为它认识的面建，形制相同） | `.zcode/skills/<自建>` → 仓库 |
| `link` | POSIX | 符号链接（词法相对路径，两级形制） | `sync-wsl.sh` | `.claude/skills/<名>` → `../../.agents/skills/<名>` |
| `storage` | 两者 | **真实目录**（第三方的存放地） | `npx skills` | `~/.agents/skills/<第三方>` |

一个名字在面里的**形态由来源决定**：链接类来源（自建 / 第二个来源 / 已进仓库层的第三方）必须是**链接**；`manual` 是**真实副本**；`storage` 本身就是真实目录。形态错 = 那个来源在那一面没被正确承载。

## 四、不变量（违反时的标记就是判定的词汇表）

| # | 不变量 | 违反时的表现 |
|---|---|---|
| **I1** | 内容只有一个权威位置；面里的东西永远可以删了重建 | 结构上不可违反；手工改面会被 I2 抓住 |
| **I2** | 链接类来源在**链接面**里必须是链接 | `[STALE]`（被真实副本顶替，或迁移做了一半） |
| **I3** | 该面声明的来源**必须都在**且能解析 | `[MISS]` / `[BRK ]` / `[WARN] surface missing`（required 面计入退出码） |
| **I4** | 多出来的东西**只提醒、不失败** | `[EXTRA]` / `[UNK ]` / `[NEW?]` |
| **I5** | 派生状态不手写；正文不写易腐数字 | 生成块标记；正文里的数量/清单即漂移起点 |
| **I6** | 两个管理器不越界：npx 只写仓库层，本体系只写面 | `[STALE]` / `[CONFLICT]` |
| **I7** | 第三方池与锁**按平台**取 | 跨平台差异是常态，不是缺口 |

## 五、生命周期：任何改动都走同一四拍

```
① 改权威    在唯一的源头改内容（仓库 / 调 npx / 人给）
② 改声明    谁变了改谁（清单 / 登记表 / 锁；自建不用改——仓库即列表）
③ 跑机制    对应端的同步脚本（第三方先 npx 再同步）
④ 读判定    两端 check_distribution.py 退出码 0；提醒逐条裁定
```

四种操作只是这四拍的不同填法：

| 操作 | 关键标记 |
|---|---|
| 自建 新增 / 改名 / 退役 / 改内容 | 改名查 `[CONFLICT]`；退役看 `[BRK ]`；改内容只需 push + 他端 pull |
| 第三方 引入 / 更新 / 卸载 | 迁移（副本→链接）看 `[STALE]`；`-y` 不带 `--skill` 会装整仓 |
| 手工 入账 / 恢复 | 有账即不再算"多余"；恢复只能从另一个面复制 |
| 面 新增 / 下线 | 新增看 `[WARN] surface missing`；下线用 `--retire`（只打印） |

**多端必然的中间态**：只在一端同步过时，另一端必然报 `[MISS]`——这是预期，不是故障。

## 六、机制契约（谁做什么、绝不做 什么）

| 机制 | 做 | 绝不做 |
|---|---|---|
| `npx skills` | 仓库层的增删改 + 写锁 | 不写平台面（面归本体系）；不碰自建 |
| `ensure_junctions.ps1` | Windows 面的 junction 增 / 清、懒建技能根 | 不删真实副本（只点名）；不碰 `storage` 面 |
| `sync-wsl.sh` | POSIX 面的链接增 / 清 + 刷 AGENTS.md + 对账 + 锁快照 | 同上；不清非本体系链接 |
| `gen-skills-table.py` | 生成 README / AGENTS.md 的生成块 | 不写清单；不在仓库里留 `.bak` |
| `check_distribution.py` | 只读判定；`--retire` 干跑 | **永不写文件** |

## 七、盲区总账（原先散落在多处，此处汇总）

| 盲区 | 影响 | 处置 |
|---|---|---|
| 只在**名为 `skills`** 的目录里发现未登记面（深度 ≤4） | 别的命名的目录不会被 `[NEW?]` 点名 | 接受：发现机制只覆盖主流约定 |
| `platform` 同时表示"操作系统"和"谁的家目录" | 在 WSL 里装的 `~/.zcode` / `~/.dsh` 两端都不审 | 接受（当前不在 WSL 用这两个工具） |
| 跨 OS 同名目录内容可能不同 | 同名条目未必是同一个技能 | 靠对账点名 |
| `npx skills` 的 agent 表里没有 `dsh` / `workbuddy` | 那两个面的第三方 CLI 不会物化 | 已由同步脚本建链覆盖 |
| 工具自带市场 / 云端会物化或复活条目 | 可能与我们的链接抢路径 | `[STALE]` / `[UNK ]` 是防线；去工具界面删 |
| 迁移时 CLI 认为"已安装"就静默跳过（连手工副本也算） | 顺序错一步会做半截而不报错 | 固化脚本：先移出副本 → add → 建链 → 销账 |

## 八、信噪比约定

对账输出里存在**已裁定、长期不变**的提醒（工具自带市场件、未纳入管理的 marketplace 等）。它们每次都会打印，长期会把真信号稀释掉。约定：

- 这类项**必须**在分发清单对应条目的 `note` 里写明"已裁定：非本体系 / 其自身机制管理"，读者据此跳过；
- 一旦某个"已知噪音"的**数量或构成变了**，那就是新信息，必须重新裁定；
- 失败级（`[MISS]` / `[STALE]` / `[BRK ]` / `[WARN] required`）永远不许被噪音淹没——它们计入退出码，是唯一的"完成"判据。
